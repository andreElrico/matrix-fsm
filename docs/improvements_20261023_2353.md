# TDD Execution Plan: Hardening `@matrix-fsm` (7 Red-Green-Refactor Cycles)

**Mode:** Strict Test-Driven Development (TDD)  
**Rule of Engagement:** The Public API of `@matrix-fsm` is locked. For every work package below, we strictly execute the **🔴 RED $\rightarrow$ 🟢 GREEN $\rightarrow$ 🔵 REFACTOR** loop in order:

1. **🔴 RED:** Write the exact unit, type, or AST test described below first. Run `pnpm nx test <project>` and verify that the test **fails** (and fails for the expected reason). Do NOT touch implementation files before the failing test exists.
2. **🟢 GREEN:** Write the minimal, cleanest implementation code in `src/lib/` to make the failing test pass.
3. **🔵 REFACTOR:** Clean up internal duplication while keeping `pnpm nx run-many -t test,lint,build` 100% green before moving to the next cycle.

## Cycle 1: Run-to-Completion FIFO Event Queue (Synchronous Re-Entrancy Protection)

### Warum?

Ruft eine synchrone Methode in `{ call: (m) => m._triggerNext }` (oder ein synchron feuernder Callback) noch **während** einer laufenden Transition sofort wieder `send('NEXT_EVENT')` auf, überholt derzeit der innere `send()`-Aufruf den äußeren auf dem Call-Stack. Das verletzt das _Run-to-Completion_-Axiom von State Machines. Zudem muss beim Aufruf von `call` während eines Zustandswechsels der Zielzustand (`currentState = evaluation.nextState`) bereits konsistent gesetzt sein.

### 🔴 Step 1 (RED): Failing Test in `packages/core/src/lib/core.spec.ts`

Füge folgenden Test hinzu, der die synchrone Re-Entrancy reproduziert:

```typescript
it('processes synchronous re-entrant send() calls strictly in FIFO order (Run-to-Completion)', () => {
  const orderLog: string[] = [];
  let runnerRef!: ReturnType<typeof createMachineInstance>;

  const reentrantFSM = createFSM<{
    events: { START: void; AUTO_ADVANCE: void };
    states: 'idle' | 'step1' | 'step2';
    methods: { _onEnterStep1: () => void; _onEnterStep2: () => void };
  }>()({
    id: 'reentrant',
    initial: 'idle',
    transitions: [
      ['idle',  'START',        'step1', { call: (m) => m._onEnterStep1 }],
      ['step1', 'AUTO_ADVANCE', 'step2', { call: (m) => m._onEnterStep2 }],
    ],
  });

  runnerRef = createMachineInstance(reentrantFSM, {
    context: {},
    methods: {
      _onEnterStep1: () => {
        orderLog.push(`in-method-1:state=${runnerRef.getState()}`);
        // Synchroner re-entranter send()-Aufruf NOCH WÄHREND der erste Übergang läuft!
        runnerRef.send('AUTO_ADVANCE');
        orderLog.push('after-nested-send-in-method-1');
      },
      _onEnterStep2: () => {
        orderLog.push(`in-method-2:state=${runnerRef.getState()}`);
      },
    },
  });

  runnerRef.send('START');

  // Erwartung:
  // 1. Erst läuft Transition 1 ('idle' -> 'step1') inkl. _onEnterStep1 KOMPLETT zu Ende.
  // 2. Erst DANACH wird das eingereihte 'AUTO_ADVANCE' ('step1' -> 'step2') aus der FIFO-Queue verarbeitet!
  expect(runnerRef.getState()).toBe('step2');
  expect(orderLog).toEqual([
    'in-method-1:state=step1',
    'after-nested-send-in-method-1',
    'in-method-2:state=step2',
  ]);
});
```

### 🟢 Step 2 (GREEN): Implementation in `packages/core/src/lib/runner.ts` & `packages/angular/src/lib/with-state-machine.ts`

1. Aktualisiere den Runner (`runner.ts` sowie `createScopedMachineRunner` in `with-state-machine.ts`) so, dass bei einem Zustandswechsel (`!evaluation.stayed`) `onExit[prevState]` und `currentState = evaluation.nextState` bereits vor dem Aufruf von `call` konsistent gesetzt sind.
2. Unterstütze in `MachineInstance` sowohl `state()` als auch `getState()` sowie in `MachineInstanceHooks` sowohl `initialContext` als auch `context`.
3. Baue eine leichtgewichtige FIFO-Event-Queue (`const eventQueue: Array<{ event: string; payload: unknown; fromChildOutput: boolean }> = []` + `let isProcessing = false`) in den Runner ein:
   - Wenn `isProcessing === true` ist, reiht `send(event, payload)` das Event nur in `eventQueue.push(...)` ein und kehrt sofort zurück.
   - Die äußere `while (eventQueue.length > 0)`-Trampolin-Schleife arbeitet das nächste Event erst ab, wenn der aktuelle Übergang vollständig abgeschlossen ist (`try ... finally { isProcessing = false }`).

## Cycle 2: Single Mutation Mechanism in Column 4 (`call` Only, Forbid `patch`)

### Warum?

Um kognitive Reibung zu verhindern, darf es für synchrone State-Updates nur **einen** kanonischen Weg geben: benannte Methoden via `{ call: (m) => m._method }`. Inline-`patch`-Lambdas in Spalte 4 sind verboten.

### 🔴 Step 1 (RED): Failing Type-Test in `packages/core/src/lib/core.spec.ts`

Schreibe einen Compile-Time-Test mit `// @ts-expect-error`, der sicherstellt, dass `{ patch: ... }` in `TransitionOptions` von TypeScript abgewiesen wird:

```typescript
it('rejects inline patch option in column 4 in favor of call', () => {
  createFSM<{
    events: { INC: void };
    states: 'idle';
    context: { count: number };
  }>()({
    id: 'noPatch',
    initial: 'idle',
    transitions: [
      // @ts-expect-error — 'patch' does not exist in TransitionOptions; use 'call' instead
      [
        'idle',
        'INC',
        stay(),
        { patch: (ctx: { count: number }) => ({ count: ctx.count + 1 }) },
      ],
    ],
  });
});
```

### 🟢 Step 2 (GREEN): Implementation in `packages/core/src/lib/types.ts`, `fsm.ts`, `runner.ts` & `with-state-machine.ts`

1. Entferne `patch` und `PatchResult` aus `TransitionOptions` (`types.ts`) sowie die Laufzeit-Auswertung von `options?.patch` (`fsm.ts`, `runner.ts`, `with-state-machine.ts`).
2. Migriere bestehende Test-Maschinen in `core.spec.ts` und `with-state-machine.spec.ts`, die noch Inline-`patch` nutzten, auf benannte Methoden via `{ call: (m) => m._method }`.

## Cycle 3: ESLint Rules for the Sandwich Pattern (`pure-machine-definition` & `no-conflicting-final-output`)

### Warum?

1. Im neuen Sandwich-Pattern (`createMachineFeature` in `*.feature.ts` oder beliebigen Dateien) sind `inject()`, `patchState()` und Service-Imports in `methods` und `tasks` ausdrücklich erwünscht – nur der `transitions: [...]`-Block oben im Sandwich muss zu 100 % frei von `inject()` bleiben!
2. Außerdem darf `finalState('CANCELLED')` (mit String-Argument $\neq$ `'DONE'` in Spalte 3) niemals gleichzeitig mit `{ output: [...] }` in Spalte 4 kombiniert werden.

### 🔴 Step 1 (RED): Failing RuleTester Cases in `packages/eslint-plugin/src/lib/eslint-plugin.spec.ts`

1. Erweitere den Test von `pure-machine-definition`:
   - **Valid Case:** Ein `createMachineFeature`-Aufruf, der oben `import { inject } from '@angular/core'`, `import { patchState } from '@ngrx/signals'` und `import { ApiService } from './api.service'` importiert und in `tasks: (api = inject(ApiService)) => ...` nutzt, während `transitions: [...]` rein deklarativ bleibt (auch ohne spezielle Dateiendung).
   - **Invalid Case:** Ein `createMachineFeature`-Aufruf, der `inject(ApiService)` **innerhalb** des `transitions: [...]`-Arrays aufruft.
2. Füge einen neuen Test-Block für die Regel `no-conflicting-final-output` hinzu:
   - **Valid Cases:**
     - `['brewing', 'DONE', finalState(), { output: ['READY', (ctx) => ctx.result] }]`
     - `['brewing', 'CANCEL', finalState('CANCELLED')]`
   - **Invalid Case:**
     - `['brewing', 'CANCEL', finalState('CANCELLED'), { output: ['READY', (ctx) => ctx.result] }]`

### 🟢 Step 2 (GREEN): Implementation in `packages/eslint-plugin`

1. Passe `packages/eslint-plugin/src/lib/rules/pure-machine-definition.ts` an:
   - Prüfe im AST, ob die Datei `createMachineFeature` verwendet (oder eine Exempt-Datei wie `*.feature.ts` / `*.store.ts` ist). In diesem Fall sind Datei-weite Imports von `@angular/*`, `@ngrx/*` und `*.service` erlaubt.
   - Verboten bleiben `inject()`-Aufrufe **innerhalb** jedes `transitions: [...]`-AST-Teilbaums (auch in `*.feature.ts` / `createMachineFeature`) sowie überall in reinen `createFSM`-Dateien (`*.machine.ts`) ohne `createMachineFeature`.
2. Implementiere `packages/eslint-plugin/src/lib/rules/no-conflicting-final-output.ts` und registriere sie in `packages/eslint-plugin/src/index.ts` (inkl. `configs.recommended`).

## Cycle 4: Lightweight Unit-Test Harness for Sandwich Features (`createFeatureTester`)

### Warum?

Ein `createMachineFeature`-Artefakt enthält `tasks: (api = inject(CoffeeShopApiService)) => ({ ... })`. Wir wollen Sandwich-Maschinen in reinen, blitzschnellen Vitest-Unit-Tests (< 2ms) **ohne Angular `TestBed`** testen können, indem wir `inputs` und gemockte `tasks` direkt übergeben.

### 🔴 Step 1 (RED): Failing Test in `packages/angular/src/lib/with-state-machine.spec.ts`

Schreibe einen Test, der `baristaFSM` komplett **ohne `TestBed`** über `createFeatureTester` instanziiert und testet:

```typescript
it('tests a createMachineFeature in pure Vitest without Angular TestBed via createFeatureTester', async () => {
  const tester = createFeatureTester(baristaFSM, {
    inputs: { drink: { id: 'espresso', name: 'Espresso', price: 3 } },
    tasks: {
      brewingCoffee: async (ctx) => ({
        baristaResult: { drinkName: ctx.drink.name, brewedAt: 12345 },
        error: null,
      }),
    },
  });

  expect(tester.state()).toBe('ticketQueued');
  expect(tester.context().drink.name).toBe('Espresso');

  tester.send('START_BREWING');
  expect(tester.state()).toBe('brewingCoffee');

  // Warte auf Abschluss des gemockten Tasks:
  await tester.flushTasks();

  expect(tester.isCompleted()).toBe(true);
  expect(tester.emittedOutputs()).toEqual([
    {
      type: 'COFFEE_READY',
      payload: {
        drinkName: 'Espresso',
        result: { drinkName: 'Espresso', brewedAt: 12345 },
      },
    },
  ]);
```

### 🟢 Step 2 (GREEN): Implementation in `packages/angular/src/lib/with-state-machine.ts`

Implementiere und exportiere `createFeatureTester(feature, { inputs?, stateOverride?, tasks?, debug? })` in `@matrix-fsm/angular`:

- Erzeugt den internen `signalState` mit `{ ...feature.state, ...inputs, ...stateOverride }` (sodass `patchState` in `feature.methods` 1:1 funktioniert).
- Nutzt die übergebenen `tasks`-Mocks anstelle der DI-behafteten `feature.tasks`-Factory (sodass `inject()` in den Default-Parametern von `feature.tasks` gar nicht erst ausgeführt wird; kein `TestBed` / `EnvironmentInjector` nötig!).

## Cycle 6: Declarative Timers (`after(ms)`) with Automatic Cleanup on State Exit

### Warum?

Zeitgesteuerte Übergänge (Auto-Dismiss nach 5s, Retry-Cooldown nach 2s, Timeout) sollen ohne künstliche `awaiting()`-Boilerplate-Tasks direkt als `['coffeeReady', after(5000), 'idle']` in der Matrix stehen können. Verlässt die Maschine den Zustand vor Ablauf der Zeit, muss der Timer automatisch per `clearTimeout` abgeräumt werden (0 Race Conditions!).

### 🔴 Step 1 (RED): Failing Timer & Cleanup Tests in `packages/core/src/lib/core.spec.ts`

```typescript
describe('declarative timers with after(ms)', () => {
  beforeEach(() => vi.useFakeTimers());
  afterEach(() => vi.useRealTimers());

  it('automatically transitions after the specified delay and cancels stale timers on early exit', () => {
    const timerFSM = createFSM<{
      events: { SHOW: void; DISMISS: void };
      states: 'idle' | 'toastVisible';
    }>()({
      id: 'toast',
      initial: 'idle',
      transitions: [
        ['idle',         'SHOW',      'toastVisible'],
        ['toastVisible', 'DISMISS',   'idle'],
        ['toastVisible', after(3000), 'idle'],
      ],
    });

    const instance = createMachineInstance(timerFSM, { context: {} });

    // 1. Besuch: Wird nach 2000ms manuell abgebrochen -> Timer MUSS gekillt werden!
    instance.send('SHOW');
    expect(instance.getState()).toBe('toastVisible');
    vi.advanceTimersByTime(2000);
    instance.send('DISMISS');
    expect(instance.getState()).toBe('idle');

    // 2. Besuch bei t=2500ms: Der alte Timer von Besuch 1 darf NICHT bei t=3000ms feuern!
    vi.advanceTimersByTime(500);
    instance.send('SHOW');
    expect(instance.getState()).toBe('toastVisible');

    vi.advanceTimersByTime(2999);
    expect(instance.getState()).toBe('toastVisible'); // Nach 2999ms im 2. Besuch noch offen!

    vi.advanceTimersByTime(1);
    expect(instance.getState()).toBe('idle'); // Exakt nach 3000ms im 2. Besuch geschlossen!
  });
});
```

### 🟢 Step 2 (GREEN): Implementation in `primitives.ts`, `types.ts`, `fsm.ts`, `runner.ts`, `with-state-machine.ts` & `eslint-plugin`

1. Füge `after<const TMs extends number>(ms: TMs): AfterNode<TMs>` (`{ __type: 'after', __kind: 'after', ms, id: '__after_${ms}__' }`) und `isAfterNode` in `packages/core/src/lib/primitives.ts` hinzu (und re-exportiere `after` in `@matrix-fsm/angular`).
2. Erlaube `AfterNode<number>` in Spalte 2 (`VIA`) von `TransitionRow` (`types.ts`) und löse `isAfterNode(via) ? via.id : String(via)` in `fsm.ts` auf.
3. Im Runner (`runner.ts` und `with-state-machine.ts`):
   - Wenn ein State betreten wird, prüfe alle Zeilen der Matrix mit `FROM === currentState` und `isAfterNode(VIA)`.
   - Starte für jeden gefundenen `AfterNode` einen `setTimeout`, der nach `ms` Millisekunden das interne Timer-Event (`afterNode.id`) an die Maschine sendet.
   - Sobald der State verlassen wird (oder `reset()` / `destroy()` aufgerufen wird), rufe für alle aktiven Timer dieses States sofort `clearTimeout(timerId)` auf!
4. Aktualisiere `packages/eslint-plugin/src/lib/ast-utils.ts` (`extractNodeKey`), damit `after(3000)` als gültiger `VIA`-Knoten (`after(3000)`) für die Gruppierungs-, Fallback- und Unreachable-Regeln erkannt wird.

## Cycle 7: Parallel Actor Orchestration (`each()`) for `createMachineFeature`

### Warum?

`each('items', childFeature)` soll nahtlos mit dem neuen `createMachineFeature`-Sandwich funktionieren: Für jedes Element im Array wird ein isolierter Sub-Akteur gestartet, bei `'ALL_DONE'` geht der Parent weiter, und bei einem Parent-Interrupt (`CANCEL`) werden alle laufenden Child-Tasks sofort per `AbortSignal` abgebrochen.

### 🔴 Step 1 (RED): Failing Test in `packages/angular/src/lib/with-state-machine.spec.ts`

Schreibe einen Test, in dem eine Parent-Maschine über `each('drinks', baristaFSM)` zwei parallele `baristaFSM`-Akteure startet:

1. Prüfe, dass `ALL_DONE` erst feuert, wenn **beide** Akteure ihren `finalState()` erreicht haben.
2. Prüfe in einem zweiten Testfall, dass ein Parent-Interrupt `[each('drinks', baristaFSM), 'CANCEL', 'idle']` sofort die `AbortSignal`s **aller** laufenden `baristaFSM`-Instanzen abbricht (`expect(abortedDrinks).toEqual(['espresso', 'latte'])`).

### 🟢 Step 2 (GREEN): Implementation in `packages/angular/src/lib/with-state-machine.ts` & `runner.ts`

- Verbinde `each(arrayKey, childFeature)` mit dem `MachineFeature`-Actor-Spawner in `withStateMachine`.
- Übergib jedem gespawnten `createMachineFeature`-Akteur das jeweilige Array-Element sowohl direkt (Properties) als auch unter dem singulären Key (`drinks` $\rightarrow$ `drink`) und `selectedDrink` (falls nicht explizit via `input` gemappt), leite Events an aktive `each`-Kinder weiter, sammle deren Ergebnisse bei `ALL_DONE` und rufe beim Verlassen des `each`-Zustands (z. B. durch `CANCEL`) auf allen noch laufenden Instanzen den Hard Kill (`abort()` + `destroy()`) auf.
